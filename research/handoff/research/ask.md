# When should a coding agent ask?

**Verdict:** Ask rarely, ask early, and ask only about gaps that would make a different build. One targeted goal-level question, asked before work starts, recovers most of the lost accuracy. Asking by default, asking late, or bundling questions adds little and can do worse than not asking. Caveat: every study below uses LLM-simulated users. No real-developer RCT exists.

## Findings

- **Asking helps when the gap matters.** In Ambig-SWE, interaction on underspecified SWE-bench tasks gave "up to 74%" gains, but models struggle to tell well-specified tasks from underspecified ones (https://arxiv.org/abs/2502.13069v3). ClarifyGPT (FSE 2024) asks only when sampled solutions disagree. GPT-4 MBPP pass@1 rose from 70.96 to 80.80 (https://arxiv.org/pdf/2310.10996).
- **Selective asking nearly matches full spec.** In "Ask or Assume?", Sonnet 4.5 with an intent agent scored 69.4%, against 70.8% fully specified and 61.2% single-agent. It still asked on about 69% of tasks (https://www.alphaxiv.org/abs/2603.26233).
- **Timing dominates.** A goal clarification at 10% of the trajectory gave pass@3 0.78 (oracle 0.80). At 50% it gave 0.44, close to never asking (0.40). Input clarification at 90% did worse than never asking (0.25 vs 0.33) (https://arxiv.org/pdf/2605.07937).
- **Over-asking is real.** In LHAW, GPT-5.2 asked the most, got the lowest gain per question, and 38% of its asking trials were flagged as over-clarification. Gemini-3-Pro asked in 18% of trials and got the best gain per question. Compound questions were the top failure mode. Heavy plan-and-execute scaffolds sometimes hurt easy tasks (https://arxiv.org/pdf/2602.10525). Forcing a question on every query collapsed F1 to 0.177 (https://arxiv.org/pdf/2609.24290). One model reached 0.74 success but -4.24 regret-reward over about 4 turns (https://www.alphaxiv.org/abs/2607.21143.md).
- **Under-asking is the default.** Models recognise ambiguity but "rarely ask" (https://huggingface.co/papers/2605.25284). Under-clarification rises to about 48% in failed LHAW trials.
- **Value of information.** A parameter-free VoI rule weighs expected utility gain against the user's cognitive cost. It matched or beat tuned baselines (ACL 2026, https://preview.aclanthology.org/ingest-acl/2026.acl-long.1987/). Poorly formulated questions cause "user frustration" (https://arxiv.org/abs/2402.01934v1). I found no specific NeurIPS-2025/26 paper showing that elicitation lowers accuracy. The closest evidence is the forced, late and over-asking results above.
- **Products.** Claude Code's AskUserQuestion takes 1-4 multiple-choice questions with 2-4 options each, is "especially common in plan mode", and isn't available to subagents (https://code.claude.com/docs/en/agent-sdk/approvals). Cursor's plan mode researches first, then asks (https://cursor.com/blog/plan-mode). Its users want the rate tunable both ways (https://forum.cursor.com/t/feature-request-for-a-way-to-tune-how-prone-an-agent-in-plan-mode-is-to-ask-questions-to-the-user-about-things-it-would-like-clarification-on/156945). Devin asks when its confidence isn't green. Green correlates with merged PRs about 2x as often as red (https://cognition.com/blog/devin-2-1). All three ask before execution, which matches the timing data.

## Three rules: ask only what changes the build

1. **Divergence test.** Sketch the build under each plausible answer: the files, the interfaces and the test outcomes. If the diffs match, or differ only in ways that take under 5 minutes to change, don't ask. State the assumption in the plan.
2. **Front-load or forgo.** Explore the code first, then batch the goal and constraint questions into one AskUserQuestion before the first edit. Keep each question atomic and multiple-choice. After about 30% of the work, ask only when blocked. Otherwise log the assumption in the PR.
3. **Build both when that's cheaper than asking.** If the branches diverge but each is small and reversible, build both behind a flag or in two worktrees, run the tests, and offer a one-line choice. Ask up front only when a wrong guess is expensive or irreversible: schema, public API, data deletion, security, or spend.
